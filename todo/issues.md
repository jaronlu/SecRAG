# 一、最应该先修的问题

这里的 **P1** 表示应优先修复、已经影响功能或安全语义；**P2** 表示应在工程化或扩大使用前解决。

## 1. P1：答案缓存没有绑定会话上下文，而且绕过了正常的合规和审计流程

**位置：** `src/api/main.py::assistant_qa`、`src/utils/semantic_cache.py::lookup/store`

当前缓存查找使用的是：

```python
cache.lookup(request.query, role=user.role)
```

缓存记录中没有用户、客户、会话上下文、知识库版本或授权版本。匹配的是**原始问题的相似度和角色**，不是完成指代消解后的完整请求。

一个很容易遇到的错误场景：

> 会话 A 先讨论产品 A，再问“它的风险等级是什么？”
> 会话 B 先讨论产品 B，再问同一句话。
> 两次原始问题完全相同、角色相同，但正确答案不同。

当前缓存无法区分这两种情况。**这在现有单用户多会话下就会发生；未来接入同角色多用户后，还会增加跨用户复用个性化回答的风险。**后者是条件性风险，不是本次已经验证的实际数据泄漏。

更关键的是，缓存命中后直接返回：

```python
"compliance": {"passed": True}
```

而缓存写入条件实际上只是答案非空且长度大于 10，没有落实注释中“验证通过才缓存”的限制。命中后也不会执行图里的会话保存和审计节点。于是，原本的合规拒答可能被缓存后标记成“合规通过”，返回的 `turn_id` 也没有对应的正常持久化记录。这里不等于原始危险答案一定泄漏，但**合规状态和审计语义已经失真**。

**建议：**

先默认关闭最终答案的语义缓存，保留经过授权的检索结果缓存。重新启用答案缓存时，至少做到：只缓存明确允许缓存的成功终态；把身份与授权范围、客户上下文、规范化问题、上下文摘要哈希、知识库版本纳入匹配条件；保存真实的验证与合规结果；缓存命中仍然执行本轮会话保存和审计。

**不要只补一个 `user_id` 就认为修好了。**同一个用户的两个不同会话仍然可能发生上下文串用。

## 2. P1：SPA 通配路由注册过早，会截走后面的 GET 接口

**位置：** `src/api/main.py::spa_catch_all`

`@app.get("/{full_path:path}")` 注册在 `/health`、`/metrics`、会话消息读取和部分管理 GET 接口之前。该函数对 API、健康检查等路径抛出 404，但抛出 404 **不会让框架继续尝试后面的路由**。Starlette 是按注册顺序匹配路径的。([Starlette](https://www.starlette.dev/routing/))

我用相同路由结构做了最小复现：


| 请求                                     | 实际结果 |
| -------------------------------------- | ---- |
| `GET /health`                          | 404  |
| `GET /v1/assistant/threads/t/messages` | 404  |
| `POST /v1/assistant/qa`                | 200  |


这不是所有 API 都会失效：提前 `include_router` 的入库接口不属于同一情况，POST 问答也不会被 GET 通配路由这样截走。

但 Docker 的健康检查恰好访问 `/health`，因此这个问题还会让容器健康检查失败，而不仅仅是某个页面打不开。

**建议：**将 SPA fallback 放到所有业务路由之后，或者把前端静态服务独立出来。补测试时必须通过 `TestClient`/ASGI 发真实 HTTP 请求，不能只直接调用 `health_check()` 或检查路由名称是否存在。

## 3. P1：前后端 SSE 协议没有对齐，默认流式问答不能正常显示答案

**位置：** `src/api/main.py::assistant_qa_stream`、`frontend/src/api.ts::streamQuestion`、`frontend/src/pages/ChatPage.tsx::handleSend`

后端的事件形式是：

```text
event: answer
data: {"answer": "...", "citations": [...], ...}
```

但前端解析时忽略了 `event:` 行，只解析 `data:` 的 JSON；之后页面又判断 `event.type === 'answer'`，并读取 `event.data`。**后端 JSON 中既没有这个 `type`，答案字段也叫 `answer` 而不是 `data`。**因此正常事件不会进入前端的答案处理分支，而页面默认开启流式模式。协议最小复现已经确认这一点。

后端还有另一处终态遗漏：流式接口只在 `compose` 节点输出答案，但图中的 `clarify` 和 `permission_denied_response` 会直接进入会话保存、跳过 `compose`。所以**澄清和权限拒绝可以正常生成，却没有对应的 SSE answer 事件**。

**建议：**定义唯一的流式协议，并让前后端共同遵守。例如统一使用 `type + payload`，或者正确解析 SSE 的事件名；不要混用。最终响应应该来自统一的终态模型，而不是硬编码“只有 compose 才算回答”。正常回答、澄清、权限拒绝、验证失败和工具超限，都应有明确的终态事件。

### 同一部分还有几处 REST 契约错配


| 功能         | 当前问题                                                                          |
| ---------- | ----------------------------------------------------------------------------- |
| 角色切换       | 前端提供 `demo-analyst`、`demo-technical`、`demo-admin`，后端都不接受；技术角色实际是 `demo-tech`。 |
| 会话列表       | 前端调用 `GET /v1/assistant/threads`，当前后端只有创建会话的 POST，没有对应列表处理函数。                 |
| 知识库搜索      | 前端默认发 GET，后端注册的是 POST。                                                        |
| 删除会话       | 后端成功返回 204，前端通用请求函数仍执行 `res.json()`，会把成功删除当成解析错误。                             |
| 自动创建后的连续对话 | 未显式新建会话时，问答返回的 `thread_id` 没有写回当前会话状态，后续问题可能继续创建新会话。                          |


这些不是 UI 美化问题，而是接口对接缺陷。建议从 OpenAPI 生成或校验前端类型，并增加真正跨前后端边界的契约测试。

## 4. P1：BM25 使用了错误的元数据字段过滤来源

**位置：** `src/retrieval/hybrid_retriever.py::retrieve`

BM25 结果过滤用的是“检索源名称是否包含在 `metadata.source` 中”。

但你的数据模型区分了两个字段：


| 字段                 | 实际含义                                    |
| ------------------ | --------------------------------------- |
| `source`           | 文件路径、来源 URL 等                           |
| `retrieval_source` | `report_search`、`product_search` 等逻辑检索源 |


例如，文档的 `source` 可以是 `data/raw/reports/example.pdf`，而 `retrieval_source` 是 `report_search`。当前代码检查路径字符串是否包含 `report_search`，会把本应保留的 BM25 结果过滤掉。入库代码已经明确分别维护这两个字段。

**影响：**配置上启用了 BM25，正常文档的 BM25 命中却可能无法进入融合。这不是补齐 `jieba`、`rank-bm25` 依赖就能解决的问题。

**建议：**使用 `META_RETRIEVAL_SOURCE` 做精确匹配，并尽量在候选截断之前落实来源过滤。至少增加一个使用真实入库元数据结构的测试，不能让测试数据恰好把 `source` 写成 `report_search`，掩盖字段混淆。

## 5. P1：RRF 排序没有被保留，后续又混用了不同量纲的原始分数

**位置：** `src/retrieval/bm25_retriever.py::rrf_fuse`、`src/agents/nodes.py::grade_and_filter`

`rrf_fuse()` 计算了融合分数并据此排序，但返回的仍然是原始结果对象，没有保存融合分数。随后 `grade_and_filter()` 又按原始 `score` 排序、过滤和截断候选池。

这里的原始分数有两种不同含义：向量结果是相似度，BM25 结果是 BM25 原始分数。把它们直接比较，不是有效的融合排序。

我的最小复现中，RRF 得到的次序是：

```text
同时命中的文档 → 向量独有文档 → BM25 独有文档
```

经过后面的原始分数排序，变成：

```text
BM25 独有文档 → 向量独有文档 → 同时命中的文档
```

需要说明：当前 `grade_and_filter` **确实会尝试调用语义 reranker**，不能说项目“没有重排”。问题是它在重排之前就按混合原始分数筛选并限制候选池，被提前排除的证据无法由后续重排挽回。

**建议：**将 `vector_score`、`bm25_score`、`rrf_score`、`rerank_score` 分开存储；每个阶段明确唯一的排序依据。不要再让一个泛化的 `score` 同时承担四种含义，也不要用同一个阈值过滤这些不同分数。

## 6. P1：时间过滤器与 Chroma 的查询契约不兼容

**位置：** `src/agents/nodes.py::_time_range_to_filters`、`src/retrieval/filters.py`

当前生成的过滤器类似：

```json
{"date": {"$gte": "2024-01-01", "$lte": "2024-12-31"}}
```

存在两个问题：同一个字段表达式里放了两个操作符；范围比较的操作数是字符串。我核对了 Chroma 1.5.0 的校验源码，它要求单个操作符表达式只有一个操作符，且 `$gt/$gte/$lt/$lte` 的操作数是数值。外层增加 `$and`、但不拆开内部表达式，也不能解决问题。

**影响：**涉及日期的查询可能从正常召回退化为检索错误、空结果或后续重试，而不是实际完成时间过滤。

**建议：**入库时增加规范的数值日期字段，例如 `date_day`，查询时把上下界拆成两个条件：

```json
{
  "$and": [
    {"date_day": {"$gte": 20240101}},
    {"date_day": {"$lte": 20241231}}
  ]
}
```

这需要同时修改入库元数据和查询构造，不能只把查询字符串临时转成整数。相对日期的理解也建议显式传入当前日期和业务时区，避免让模型自行猜测“去年”“最近三个月”。

## 7. P1：数字验证存在明确误判，引用编号也可能与证据错位

**位置：** `src/utils/verifier.py`、`src/agents/nodes.py::_build_reason_system_prompt`

### 数字验证目前只是字符串包含判断

`NumberVerifier` 提取答案里的数字，再检查数字字符串是否出现在全部证据文本中。它没有绑定数值边界、正负号、单位、主体、指标或报告期。

隔离复现得到：


| 证据与答案                        | 数字校验结果 | 问题                   |
| ---------------------------- | ------ | -------------------- |
| 证据是“收入 120 亿元”，答案是“收入 20 亿元” | 通过     | `"20"` 是 `"120"` 的子串 |
| 证据是“-10%”，答案写成“10%”          | 通过     | 正负号没有绑定              |
| 证据无业务数字，答案添加 `[来源1]`         | 失败     | 引用编号被当成业务数字          |


这些结果针对的是数字校验层，不是一次真实模型问答的完整运行结果。

### 引用提取使用了另一套编号规则

生成 prompt 时，来源编号按照检索结果顺序分配；`CitationExtractor` 则按照提取后的 quote 去重，再重新编号。因此，当同一来源的两个 chunk 提取出相同 quote 时，引用列表的编号可能发生移动。

例如 prompt 中的来源顺序是 A1、A2、B，引用提取把 A1/A2 去重后变成 A、B。答案里的 `[来源2]` 原本指向 A2，展示时却可能变成 B。`SourceVerifier` 主要检查编号是否在范围内、引用是否属于当前检索集合，不能证明这条结论确实来自该编号对应的证据。

**建议：**

建立一次生成、全链路复用的证据集合，给证据分配稳定 ID，prompt、答案引用、验证器和前端都使用同一个映射。验证应面向“具体主张—具体证据”，而不是把全部证据拼成一个大字符串。

数字部分先排除引用编号和列表序号，再解析数值、单位、正负号、指标、主体及报告期。对推导值保存计算输入和公式。当前的关键词重合、数字出现、编号存在，可以保留为低成本检查，但**不应单独支撑“事实已验证”的强语义**。

## 8. P1：工具超时并没有真正限制等待时间，请求超时也不等于停止执行

**位置：** `src/agents/nodes.py::authorize_reason_tool_call`、`src/api/main.py::assistant_qa`

工具包装代码在 `with ThreadPoolExecutor(...)` 内调用 `future.result(timeout=...)`。当它超时抛异常时，需要先退出 `with`；而线程池上下文退出默认会等待任务完成。([Python documentation](https://docs.python.org/3.11/library/concurrent.futures.html))

我的最小复现设置等待超时为 **25 毫秒**、任务耗时为 **150 毫秒**，实际到超时处理分支用了约 **151 毫秒**。这证明当前结构限制了 `result()` 的等待，却没有限制整个工具包装函数的返回时间。

API 层的 `wait_for(to_thread(agent.invoke, ...))` 也要区分“客户端停止等待”和“执行已取消”：已经运行的线程不能因此被强制终止。图仍可能继续调用模型或写入会话。另外，SSE 接口虽然捕获 `TimeoutError`，但没有对应的请求级总超时包装。([Python documentation](https://docs.python.org/3.11/library/concurrent.futures.html))

**建议：**优先在实际 HTTP、数据库和工具调用中落实超时，并贯穿统一的截止时间和取消状态。请求结束后，在后续模型调用、工具调用和持久化前检查是否仍允许继续执行。无法合作式取消的重计算任务，应考虑可终止的隔离进程。

只改成 `shutdown(wait=False)` 不是完整修复，它能让调用方更快返回，但不能阻止残留任务继续消耗资源。

# 二、工程化前需要处理的 P2 问题



## 1. 缓存生命周期与知识库生命周期没有统一

BM25 的全局缓存实际使用 `id(vector_engine)` 作为键，而外层检索节点会创建新的 `HybridRetriever`。该键不是稳定的索引身份，也没有表达知识库版本。BM25 构建还需要从 collection 全量加载文档。

答案缓存默认有效期为 24 小时；已检查的入库更新路径没有同步推进缓存版本的步骤。这使文档更新、删除或授权变化与缓存可见性之间缺乏统一约束。

**建议：**用明确的 collection 身份、索引代次、模型版本和授权版本组织缓存；设置容量上限和回收策略。文档发布成功后推进知识版本，让检索缓存、BM25 和答案缓存统一失效，而不是分别等待 TTL。

## 2. 同步缓存操作直接运行在异步 API 中

`assistant_qa` 直接调用同步的 `cache.lookup/store`。缓存查询会读取该角色全部未过期记录、计算 embedding，并逐条反序列化向量、计算相似度；这些操作也不在 `agent.invoke` 的超时范围内。

**建议：**先把这些工作移到受限的执行池，并记录单独耗时，再决定是否需要向量索引或其他缓存服务。这里真正的问题是执行位置、搜索复杂度和容量边界，不是“用了 SQLite 就一定不行”。

## 3. 增量入库存在跨存储发布的失败窗口

当前顺序是：写新 chunks、删除旧 chunks、更新 SQLite registry、记录运行结果。它们不是一个跨存储原子事务。中间步骤失败时，存在向量数据与 registry 不一致、读者看到混合版本的窗口。**这是从代码顺序识别出的故障场景风险，本次没有运行故障注入。**

**建议：**把“写入新版本”与“发布新版本”分开。新版本完整写入并校验后，再切换可见版本；旧版本异步清理。同时增加对账和恢复机制，而不仅仅是将任务标记为 failed。

## 4. 权限过滤应尽量在 Top-K 截断之前完成

目前先检索 Top-K，再按角色过滤文档结果。当最高分候选全部无权访问、但更低位置存在可访问文档时，系统可能错误地进入“全部越权”终态，而不是继续找可访问证据。

**建议：**尽可能把 ACL 条件下推到向量和关键词检索，并保留结果级复核。安全系统既要测试“不可泄漏”，也要测试“有权限的内容不会被错误拒绝”。

## 5. LLM 输出缺少严格的运行时结构校验

`query_understand` 主要捕获 JSON 解析错误，但合法 JSON 不一定是正确对象。例如模型返回 `[]` 或 `null`，解析能成功，之后调用 `.get()` 就可能出错；`entities` 等内部字段也缺少严格类型约束。

**建议：**用明确的 Pydantic 模型约束查询理解与计划输出，限制枚举、数量、长度、日期和过滤器字段。把“格式不符合契约”和“没有检索到证据”分开处理，不要让它们都表现为模糊的降级结果。

# 三、哪些设计应该保留

我不建议推倒重写。以下几处设计是有价值的：

**身份与授权边界值得保留。**身份从服务端 token 绑定，而不是信任请求体角色；检索执行层和工具执行边界都有再次校验。当前 demo token 需要后续替换，但“服务端派生身份、执行层再次授权”的方向是正确的。

**主链路的拒答和持久化设计也应该保留。**`compose` 在验证或合规失败时替换答案、清空引用；入库使用内容哈希、元数据哈希及 parser/chunker/model 版本判断是否重做。这些比简单的“检索后直接生成”更有工程基础。问题主要是缓存、SSE 等新增路径没有完整复用这些约束。

我的核心架构建议是：**把“最终响应、终态、安全检查结果、会话保存、审计”收敛成统一出口。**普通 HTTP、SSE、缓存命中不应该各自维护一套业务正确性。

# 四、建议的修复顺序与验收标准


| 批次                 | 修复内容                                                | 验收标准                                            |
| ------------------ | --------------------------------------------------- | ----------------------------------------------- |
| **第一批：先让真实使用链路成立** | 暂停不安全的答案缓存；调整路由顺序；统一 SSE/REST 契约；修复角色 token 和 CI 触发 | 从前端完成创建、连续问答、澄清、权限拒绝、查看消息和删除；健康检查正常；提交能实际触发 CI  |
| **第二批：让检索与证据真正正确** | BM25 字段、RRF 分数、日期过滤、引用 ID、数字与事实绑定                   | 在固定小型语料上验证召回和排序；错误数字与错引反例被拦截；正确答案不因引用编号被误杀      |
| **第三批：补可靠性与运行边界**  | 总截止时间、取消状态、缓存代次与容量、入库发布/恢复、完整指标                     | 超时行为有界；更新与撤权后不复用旧结果；故障注入后可恢复；普通请求、缓存和流式请求都有完整记录 |


测试上，我最建议补的是**边界测试，而不是继续堆节点 mock**：真实 HTTP 路由、后端实际 SSE 字节流、使用真实元数据的 Chroma 小集成、跨会话缓存隔离、数值与引用成对反例，以及入库关键步骤失败后的恢复。

检索评估也建议分开统计召回、排序、引用准确性、拒答误判、权限误拒、跨会话污染和时效性，而不是只看一组综合指标。这样才能知道问题究竟在检索、生成、验证，还是外围接口。

**最终建议：先把“一次请求在所有入口下都使用正确身份、正确上下文、正确证据，并留下完整记录”做扎实。你现在最缺的不是更多功能，而是已有功能之间一致、可验证的契约。**
