# SecRAG 面试可用性评估

评估日期：2026-09-24  
目标岗位：AI 应用 / Agent 工程师

## 结论

这个项目已经足够作为 AI 应用 / Agent 工程师的面试项目，但还不像“真的被业务使用过”。目前缺的不是更多组件，而是一个可验证的业务闭环。

## 主要缺口

| 优先级 | 还差什么 | 面试官会怎么判断 |
|---|---|---|
| P0 | **持仓 → 每日扫描 → 影响判断 → 晨报交付**闭环 | 现在已有持仓模型和扫描 Job，但 REST、传导推理、晨报、归档仍在队列中（T-005～T-009） |
| P0 | **真实效果数据** | 检索集只有 5 条；回答集 29 条；事件漏报/误报评估还未完成（T-010），无法证明“效果好” |
| P0 | **真实数据源跑通证明** | 当前真实数据规模很小，akshare / cninfo / efinance / baostock 契约尚未真机校准（T-013） |
| P1 | **可一键演示** | 目前启动、入库、模型配置、数据准备步骤较多；面试官很难在 10 分钟内看到完整价值 |
| P1 | **生产边界与成本指标** | 缺少 p50/p95 延迟、单次成本、吞吐、失败率、缓存收益、模型调用次数 |
| P1 | **安全闭环** | Demo token、SQLite 单机、内存 checkpointer 都已诚实说明；但权限矩阵扩展和 SQL/计算器降级仍未完成 |
| P1 | **叙事收敛** | 功能很多，但“谁每天用它、节省什么时间、输出什么决策”还不够尖锐 |

## 已有优势

工程底座并不虚。当前正确命令 `uv run python -m pytest -q` 已通过 **312 tests**；权限、引用验证、合规、混合检索、审计等都能讲。

## 面试官大概率追问

1. 它到底替谁做了什么工作？
2. 比普通 RAG 好多少？数字在哪？
3. 如果今天真的接入 300 只股票，哪里会先坏？
4. 你的规则阈值和事件分级依据是什么？
5. 哪些能力是 demo，哪些已经生产可用？

## 最短补齐路线

1. 完成一条黄金路径：`用户持仓 → 扫描事件 → 影响判断 → 带引用晨报 → 合规拦截 → 审计归档`。
2. 做一个 30～100 条的真实标注评估集，至少报告召回、漏报率、误报率、引用正确率、延迟。
3. 做一个 `./demo.sh` 或录屏，启动后一次展示“授权回答、越权拒绝、每日晨报”。
4. 修正面试指南中的过时事实：它写的是 273 个测试，当前实际是 312 个。

## 一句话评价

现在是“很强的架构验证项目”；补完 P0 闭环和评估后，才会变成“有业务价值、能落地的 AI Agent 项目”。
