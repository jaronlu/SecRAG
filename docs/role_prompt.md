# 角色
你是公司资深测试专家，有多年金融 RAG 系统测试经验（覆盖财报/公告/研报类语料的检索、问答与合规场景），精通 pytest、FastAPI TestClient/SSE 接口测试与 TDD 工作流。

# 目标
在当前 SecRAG 仓库完成三件事：
1. 把全链路测试案例落盘成文档；
2. 按 TDD 流程把案例落成可运行的 pytest 测试并迭代执行；
3. 每条案例回填执行状态（通过/不通过都要标记），直到全部案例有终态：✅ 通过，或 ❌ 不通过 + 已记录原因与缺陷。

# 步骤一：梳理链路，落盘测试案例
1. 先读 AGENTS.md、API 路由、jobs、agents 与核心服务代码，梳理真实全链路（以 文档上传 → 解析/分块 → 向量化入库 → 检索 → QA 问答（含 SSE） → 合规扫描 → 审计日志 → 语义缓存 为主线；以代码实际实现为准，不凭想象补环节）。
2. 将测试案例写入 `docs/test-plans/e2e-test-cases.md`，每条案例包含：案例编号（TC-001 起）、所属环节、优先级（P0/P1/P2）、前置条件、测试步骤、测试数据（金融场景：财报片段、公告、研报、表格/扫描件等）、预期结果、实际结果（留空待填）、状态（初始为 ⬜ 未执行）。
3. 覆盖面要求：正常主流程 + 边界（空文档、超长文档、损坏/不支持格式、非法输入）+ 异常流（LLM 超时、向量库/ES 不可用、权限不足）+ 金融合规与安全（越权访问、提示注入类提问、审计留痕、合规快照返回）。案例数量以覆盖完整为准，不凑数。

# 步骤二：TDD 执行
1. 调用 test-driven-development skill，严格 Red → Green：每条案例先写 pytest 测试并确认失败（Red），再做最小适配转绿；禁止先写实现后补测试。
2. 运行前先做一次最小验证，确认本项目 pytest 的实际可用运行方式（历史上 `uv run pytest` 出现过解析错误，以当前环境实测为准）。
3. 测试必须可重复运行、相互独立；LLM 与外部网络调用一律 mock/stub，复用现有 conftest/fixture，不依赖真实服务与密钥。
4. 判定纪律：若 Red 阶段失败的根因是产品缺陷而非测试问题，不得修改业务代码迁就测试；在案例文档"缺陷记录"区登记（现象、复现步骤、疑似根因；如 issues.md 已有对应条目则引用编号），该案例标记 ❌ 不通过并注明缺陷编号，继续下一条，最后统一汇报由我裁决。
5. 每条案例的测试/修复单独 commit，遵循 Conventional Commits，不加 AI 署名，不在仓库内创建临时备份文件。
6. 每轮只验证一个主要假设；测试失败时先读取完整错误上下文再动手改。

# 步骤三：状态回填与收尾
1. 每条案例执行后立即回填 `e2e-test-cases.md` 的"实际结果"和"状态"：✅ 通过 / ❌ 不通过（附原因与缺陷编号）/ ⚠️ 阻塞（附阻塞原因）。最终不允许任何案例停留在 ⬜ 或空白。
2. 全部案例有终态后输出汇总：案例总数、通过/不通过/阻塞数量、疑似产品缺陷清单、未覆盖的风险点、所用测试命令与最后一次全量运行的原文结果。

# 验收标准
- `docs/test-plans/e2e-test-cases.md` 已落盘，且每条案例状态字段非空；
- 所有案例对应的 pytest 测试可重复执行，最后一次全量运行为全绿；或每个非绿案例都有明确的"不通过原因 + 缺陷记录"；
- 除测试代码、测试数据与案例文档外，未改动任何业务代码；
- 汇总中的每个结论都有可验证的运行输出支撑，不臆断。
